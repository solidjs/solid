During `renderToStream`, an `<Errored>` whose `<Loading>` fails after the shell has been sent can now show its error fallback in the page before the client runs, even when the `<Loading>` is not all of its content (markup between them, a sibling beside it, other `<Loading>`s in it). Before, the stream sent an empty fragment for the failed `<Loading>`, the page kept the content with that position blank, and the fallback appeared only when the client hydrated (#5223).

This applies only to a fallback that is plain markup: finished as it renders, with no `<Loading>` of its own, and registering nothing (no head tags or stylesheets, inline styles, lazy modules or serialized values). The nearest `<Errored>` sends that markup and its error. A small inline function, sent once per render with the first such fallback, finds the two ends of the `<Errored>`'s content by what they already carry (a hydration key, a `<Loading>` placeholder, or the end of the content a settled `<Loading>` rendered) and replaces that range with the fallback. The page does this only while no client runtime has started, only if the two ends are still siblings in order, and only if all of the content's keyed elements are still between them. A client that hydrates afterwards adopts the fallback without rendering it again, and recovers when the content's inputs change. The failed `<Loading>` settles as before, and nothing else in the content is cancelled.

In every other case nothing extra is sent, and the client renders the failure on hydration. The stream has the same content as before this change. The server now renders the fallback to try it, though, so code in the fallback runs, and a lazy import it starts can move a later fragment one chunk earlier. That covers: a fallback that is not plain markup; an end of the content with no key or placeholder (text, `<NoHydration>`, hand-written `ssr()` without `ssrHydrationKey()`) or one created outside the `<Errored>`; `<html>`, `<head>` or `<body>` as the content or the fallback; a transport `sink`; `noScripts`; and server components. The page itself also declines when a client runtime has already started or the parser moved the content. The server error hook hears `fallback` when the fallback is sent and `client` otherwise. As before the shell, a mapped error that makes the fallback render again unfinished sends nothing, although the hook has heard `fallback`. An `<Errored>` inside a fallback that is tried and not sent can also report the error it caught as `fallback`. A render with no such failure is byte-for-byte what it was.
